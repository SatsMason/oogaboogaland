# SatsMason character and mason's kit

SatsMason uses the approved generated stone body, a waist apron that leaves the BTC chest symbol exposed, an ash hurley, ribbed sliotar, Thor-style hammer, trowel and two chisels. The Toolbelt selector draws a tool or holsters everything. Other equipment remains visibly stored. Tools use the existing melee path; this change does not add a masonry construction simulation or new damage rules.

The small `src/characters/SatsMason.js` declaration reads immutable packed data from `src/js/satsmason-art.js`, loaded before the character registry bundle. This keeps the existing identity/scanning limits intact. The build includes both in the same self-contained page. Original textured GLBs and offline conversion sources are retained in the delivery's recovery bundle; the game uses sampled face colours and explicit normals.

Mesh colour detail is retained on the face and torso, and adaptively retained on limbs where source colours vary. The complete preview kit uses 137,063 unique mesh triangles, versus 211,061 before this pass. The isolated high-quality preview delivered 60 FPS before and after; this is not an island-wide frame-rate guarantee. The waist-apron site build is reduced from 19,274 KB / 7,769 KB gzip to approximately 16,291 KB / 6,851 KB gzip.

Tool and holster choices save through the existing local game storage. Invalid or unknown selections fall back safely. Player equipment is sent on change, including while standing still, via a bounded/rate-limited room message. Welcome snapshots and socket attachments preserve it for late join and reconnect. NPC frames use a previously reserved float for tool choice without changing their record size. Remote players show the selected tool and holstered copies; exact player strike animations are not replicated by this change.

Validation: build and changed JavaScript syntax checks; `node test/run.mjs equipment` (8/8); `node --test worker/test/*.test.mjs` (35/35); `node scripts/characters.mjs --json`. Real UI checks cover selected-tool and holster reloads, hammer action, and front/side/back walking inspection. Existing complete-suite activity failures are recorded in the local test ledger; those STOP failures were not rerun or weakened. Earlier headless Chrome startup failures still prevent claiming a full browser/performance pass. Multiplayer validation exercises the real room/client/remote-model code with mocked transport, not two live authenticated production sessions.

Review before merge: full island frame-rate and physical phone checks, complete gameplay/scene-return coverage, and a two-account staging multiplayer smoke test. Preserve rock and production until the owner explicitly approves merge/deployment. The draft PR is for manual review; no automation-policy or deployment-workflow changes belong to this character work.
